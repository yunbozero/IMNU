# 管理端计划（义卖当天用）

> 状态：**已定方向，本期未开工**。下次接着做时从这份文档开始。

## 已定方向

**管理端做在小程序里，不做单独网页。**

理由：现在的鉴权链路是「微信登录 → openid → 角色」，角色绑在 openid 上。
单独做个网页端就得再造一套密码登录 —— 那是安全敏感的新代码，
义卖一个月内不值得引入。管理端做成小程序里的一个分包即可，
复用同一套 token 和角色判断。

## 本期范围

按义卖当天的重要性排。后端状态是核对过的。

| # | 功能 | 后端接口 | 前端 | 说明 |
| --- | --- | --- | --- | --- |
| 1 | **看预定名单**（状态分组 + 搜取货码/物品/姓名） | ✅ `GET /api/admin/reservations` | ✅ **已做** | 最基础，当天最常用 |
| 2 | **改物品名额**（现场临时加减） | ✅ `POST /api/admin/item` | ❌ 待做 | 物品卖得比预期快时用 |
| 3 | **撤销误核销** | ✅ `POST /api/admin/undo-redeem` | ✅ **已做** | 志愿者扫错码/看错号时兜底 |
| 4 | **取消别人的预定** | ❌ **需新写接口** | ❌ 待做 | 学生来不了、一人占多个名额 |
| 5 | **取货码二维码** | 不用改（核销仍走 `POST /api/redeem`） | ❌ 待做 | 志愿者扫码代替手输，见下 |

已做的部分在 `miniprogram/packageAdmin/pages/reservations/`（分包 `packageAdmin`），
入口在「我的」页，只对 `deputy` 及以上显示。

- 页面上做了状态分组和本地搜索（服务端没有搜索参数；名单就几百条，本地过滤输入即出结果）。
- **按摊位筛选还没做** —— 服务端的名单行里没有摊位字段，要加得先改 `listEventReservations` 的查询。
- 「撤销核销」按钮只对 `admin` / `owner` 显示，和服务端「二级管理员不能撤销核销」保持一致。

第 4 项是本期唯一要动后端的：需要一个管理员专用取消接口
（例如 `POST /api/admin/cancel`），并且必须**复用 `cancelReservation`** 的
名额回滚逻辑，不能另写一条更新语句 —— 否则并发下的名额会算错。

### 第 5 项要先定实现方式（下次开工第一件事）

小程序里画二维码需要一个编码器，三条路：

1. **内置一个纯 JS 二维码编码器**（单文件约 10–20KB）。
   但本仓库目前**零第三方依赖**，这会是第一次引入外部代码，需要先同意。
2. **自己写** —— 二维码编码涉及纠错码和掩码，不值得手写。
3. **不做二维码，志愿者继续手输取货码** —— 取货码本身很短，手输是可接受的兜底。

## 本期明确不做

| 不做 | 原因 |
| --- | --- |
| 分时段取货 | 数据模型里没有时段字段，要先改表再改预定流程。一个月内不值得 |
| 摊位分权（志愿者只能核销自己摊位） | 现在所有志愿者权限相同。这个规模下「谁有空谁核销」更实际 |
| 设角色 / 授权志愿者（接口已有 `POST /api/admin/role`） | 本次未选。临时授权可先用脚本兜底 |

## 验收方式

用 `docs/local-dev.md` 的本地环境，逐条走：

1. 管理员身份登录 → 进管理端，能看到全部预定
2. 搜一个取货码，能定位到具体的人
3. 改一个物品的名额 → 学生端刷新后看到变化
4. 志愿者核销 → 管理员撤销 → 该预定回到「已预定」
5. 管理员取消某个学生的预定 → 学生端看到名额被释放、可重新预定

## 与备案口径的关系（别忘）

管理端只是角色和权限，**不改变小程序的主体性质** —— 有管理端不等于"组织运营"。
但界面文案要守和 C 端一样的标准：

- 不出现 公益 / 慈善 / 救助 / 义卖 / 商城 / 捐赠 这类词
- 不出现 联系方式、金额、支付 字样
- 入口只对 `admin` / `owner` 可见

`tests/miniprogram.test.mjs` 里对 C 端有这套拦截，管理端页面加进去后应当同样被覆盖。
