# 管理端计划（义卖当天用）

> 状态：**本期范围已全部做完**（2026-09）。剩下的待办见文末「还没做的」。

## 已定方向

**管理端做在小程序里，不做单独网页。**

理由：现在的鉴权链路是「微信登录 → openid → 角色」，角色绑在 openid 上。
单独做个网页端就得再造一套密码登录 —— 那是安全敏感的新代码，
义卖一个月内不值得引入。管理端做成小程序里的一个分包即可，
复用同一套 token 和角色判断。

## 本期范围

按义卖当天的重要性排。后端状态是核对过的。

| # | 功能 | 后端接口 | 前端 | 说明 |
| --- | --- | --- | --- | --- |
| 1 | **看预定名单**（状态分组 + 搜取货码/物品/姓名） | ✅ `GET /api/admin/reservations` | ✅ **已做** | 最基础，当天最常用 |
| 2 | **改物品名额**（现场临时加减） | ✅ `POST /api/admin/item` | ✅ **已做** | 物品卖得比预期快时用 |
| 3 | **撤销误核销** | ✅ `POST /api/admin/undo-redeem` | ✅ **已做** | 志愿者扫错码/看错号时兜底 |
| 4 | **取消别人的预定** | ✅ `POST /api/admin/cancel` | ✅ **已做** | 学生来不了、重复占名额 |
| 5 | **取货码二维码** | 不用改（核销仍走 `POST /api/redeem`） | ✅ **已做** | 志愿者扫码代替手输 |
| 6 | **新建物品** | ✅ `POST /api/admin/item/create` | ✅ **已做** | 义卖当天「这个也拿来卖」 |
| 7 | **物品照片** | ✅ `POST /api/admin/image` | ✅ **已做** | 列表和详情显示照片，没有照片回落 emoji + 底色 |
| 8 | **活动与摊位** | ✅ `POST /api/admin/event`、`/event/status`、`/stall` | ✅ **已做** | 建活动、开始/结束、加摊位。**一级管理员**建活动，**副主任**建摊位 |

第 6 项是后补的：一开始只做了「改」，可往库里**加**物品的唯一办法是登上服务器跑脚本 ——
组织者是没有 SSH 的。义卖当天现场加东西是常态，所以补了这个。

- 门槛和「改物品」一致（**deputy 及以上**）：都是维护物品清单，分两档只会让志愿者当天找不到人开权限。
- 建出来一律**在售**，不设草稿状态 —— 少一种「为什么学生看不到」的排查成本。
- 摊位下拉里第一项是「不指定摊位」（`stallId: null`），服务端认这个值。
- 摊位可以在界面上**新建**了（`POST /api/admin/stall`，副主任及以上）；
  但**改名和改位置**仍然只能在数据库或配置文件里改（见文末）。

### 第 7 项：物品照片

**为什么必须有「换图」而不只是「建的时候能选图」**：物品**删不掉**（只能下架），
所以图一旦配错，没有换图按钮就永远错着。物品名额页每行都有「配图 / 换图」，
已经有图的还能选「不要图片了」——否则「换图」这个动作表达不了「删掉」。

| 决定 | 理由 |
| --- | --- |
| 传 **base64 的 JSON**，不用 `wx.uploadFile` | multipart 要在零依赖下自己解析边界字符串，那是整条链路唯一麻烦的部分 |
| **客户端压缩**（`sizeType: ['compressed']` + `compressImage`） | 手机原图 3–5MB，几十件就是几百 MB，现场网络传不动 |
| 类型只看**魔术字节** | 客户端声明的 content-type 是客户端说了算的，改个扩展名就能骗过去 |
| 文件名**由服务端生成** | 拼路径不可能跑出目录，路径穿越问题从一开始就不存在 |
| 照片**不进备份** | 丢了重新传一遍就行，为它把备份脚本改复杂不值得 |
| `image` 指向不存在的文件时**拒绝** | 界面判断「有没有照片」看的就是这个字段，存了名字而文件不在会显示破图标，还**不会**回落 emoji |

三个只在线上才会暴露的坑，都写进文档并加了测试：

- `ProtectSystem=strict` 下服务只能写 `ReadWritePaths` 里的目录 —— 漏了照片目录会报
  `EROFS`，而本地没有 systemd 加固，**怎么测都正常**。
- 照片目录必须是 **755**（nginx 的 worker 是 `www-data`，不是 `bazaar`）。
- 真机上图片不显示时**先查 HTTPS 和服务器通不通** —— `<image>` 组件的 src
  **不受**服务器域名白名单限制（白名单管的是 `wx.request` 那几个 API），
  不要往「加 downloadFile 合法域名」的方向查。

### 线上数据从哪来：`scripts/init-event.mjs`

活动和摊位没有任何界面入口，全靠这个脚本：

```bash
# 只看计划，不写库
sudo -u bazaar DB_PATH=/srv/bazaar/data/bazaar.db \
  node /srv/bazaar/app/scripts/init-event.mjs /srv/bazaar/event.json

# 确认无误再加 --yes
sudo -u bazaar DB_PATH=/srv/bazaar/data/bazaar.db \
  node /srv/bazaar/app/scripts/init-event.mjs /srv/bazaar/event.json --yes
```

三条设计：

- **默认不写库**，必须显式 `--yes`。这是仓库里唯一能往生产库加活动的东西，跑错一次就是多一个活动。
- **可以重复运行**：活动/摊位/物品都按名字查重，已有的跳过。所以「再补几件」= 配置里追加几行再跑一次。
- **活动时间按北京时间解析**（写死 `+08:00`）。服务器大多是 UTC，按本机时区解析的话首页那行
  「9:00–17:00」会整整差 8 小时，而且本地怎么测都是对的。

配置模板：`deploy/event-config.example.json`。真实配置放仓库外面（`deploy.sh` 会 `git reset --hard`）。

已做的部分在 `miniprogram/packageAdmin/pages/reservations/`（分包 `packageAdmin`），
入口在「我的」页，只对 `deputy` 及以上显示。
物品相关的两个页面在 `packageAdmin/pages/items/`（名额）和 `packageAdmin/pages/item-new/`（新建）。

- 页面上做了状态分组和本地搜索（服务端没有搜索参数；名单就几百条，本地过滤输入即出结果）。
- **按摊位筛选还没做** —— 服务端的名单行里没有摊位字段，要加得先改 `listEventReservations` 的查询。
- 「撤销核销」按钮只对 `admin` / `owner` 显示，和服务端「二级管理员不能撤销核销」保持一致。

第 4 项的实现要点（已按这个做完）：

- **`POST /api/admin/cancel`**，入参 `{ reservationId, reason }`。
- **门槛：deputy 及以上**（和「改物品名额」同一级）。现场发现囤货、冒名、来不了时，
  副主任就能当场处理，不必找超管。
- **`reason` 必填（2–60 字）**，写进 `audit_logs`，并连同被取消的是谁一起记下来 ——
  同学来问"我的名额怎么没了"时才查得到。
- **必须复用 `repo.cancelReservation`**，绝不另写一条 UPDATE：名额回滚的正确性
  （只有 `reserved → cancelled` 那一次成功才加名额，否则重复点击会让名额虚增）
  全在它里面。测试直接断言"取消后名额回到预定前"，另写一条忘了加名额就会红。
- 已核销的不能直接取消，接口返回 `already_redeemed` 并提示**先撤销核销**。

**前端交互：独立的确认页**（`packageAdmin/pages/cancel/`）。取消不可逆
（名额立刻释放、东西归别人），所以不弹个框了事：确认页先把**取货码、物品、取货人、
状态、时间**摊开，再选原因。

原因做成了**选项 + 「其他」手填**：

| 选项 | 什么时候用 |
| --- | --- |
| 本人要求取消 | 同学主动来说不来了 |
| 联系不上本人 | 反复打不通、消息不回，视为放弃 |
| 重复占用（多号） | 一个人用多个微信号囤货 |
| 信息不实或冒名 | 学号/昵称对不上，或冒用他人 |
| 物品已无法提供 | 东西损坏、被拿走、临时没了 |
| 其他（手填） | 上面都不合适，拼成「其他：xxx」 |

> 列表和拼接逻辑在 `packageAdmin/utils/cancel-reason.js`。后端收的就是一个字符串，
> 所以**加/改一个原因只改那里，不用动服务、不用重启**。
> 但标签本身必须落在后端允许的 2–60 字内 —— 有测试盯着，
> 否则会出现「选完提交才被拒」这种很难查的故障。

### 第 5 项的结论：引入第三方编码器（已做）

三条路的取舍已经定了：

1. **内置纯 JS 编码器** ← **选这条**
2. 自己写 —— **没选**。二维码编码要处理 RS 纠错和掩码，而且它的故障形态特别难查：
   不报错，只是「大部分时候能扫、偶尔扫不出」。义卖现场没人能当场调这个。
3. 不做二维码 —— **没选**。当时发现志愿者端的扫码功能**早就写好了**
   （`scanCode()` → 剥非数字 → 校验 6 位 → 核销），学生端却没有任何地方生成二维码，
   等于那个「扫码」按钮必然失败。要么补齐，要么摘掉 —— 选了补齐。

落地情况：

| 事项 | 位置 |
| --- | --- |
| 编码器 | `miniprogram/packageBazaar/lib/qrcode.js`（`qrcode-generator` v1.4.4, MIT） |
| 来历与改动说明 | `miniprogram/packageBazaar/lib/README.md`（**本仓库唯一一处第三方代码**） |
| 生成矩阵 + 画到 canvas | `miniprogram/packageBazaar/utils/qr-draw.js`（纯逻辑，可测） |
| 画在哪 | `pickup-code` 页面，只在 `reserved` 状态显示；画不出来就退化成报数字 |
| 测试 | `tests/qrcode.test.mjs`（引入审查 + 矩阵合法性 + 与核销台的字符契约） |

> ⚠️ **二维码里只放那 6 位数字，不要加前缀或 URL。** 核销台扫完会把非数字全部剥掉、
> 并要求正好 6 位；放了 URL 就会被剥成一串乱数字，现场核销不了。这条有测试盯着。

## 验收方式

用 `docs/local-dev.md` 的本地环境，逐条走：

1. 管理员身份登录 → 进管理端，能看到全部预定
2. 搜一个取货码，能定位到具体的人
3. 改一个物品的名额 → 学生端刷新后看到变化
4. 志愿者核销 → 管理员撤销 → 该预定回到「已预定」
5. 管理员取消某个学生的预定 → 学生端看到名额被释放、可重新预定

## 界面文案口径（审核前定的，别忘）

### 注册信息

| | |
| --- | --- |
| 小程序名称 | **盛师猫猫** |
| 服务类目 | **工具 > 预约/报名**、**工具 > 信息查询** |

### 四条规矩

1. **界面标题必须是「盛师猫猫」。** 审核拿**名称 · 简介 · 类目 · 实际内容**四样互相对，
   界面写着别的名字 → 直接判「名称与实际功能不符」。
2. **界面文案不出现 公益 / 慈善 / 救助 / 义卖 / 商城 / 捐赠 这类词。**
   理由是**类目**：这些词把小程序指向商品交易或公益慈善，两者都不在「工具」类目里；
   而个人主体也不能涉及公益慈善类内容（网站名称当初就是因为「救助」被拒的）。
   风险不是「违禁词」，是**「实际内容与所选类目不符」**—— 最常见的驳回理由之一。
3. **界面文案不出现任何交易/金额字样**，包括「付款 / 收款 / 收费 / 费用 / 商品 / 出售」。
   ★ **否定句也算**：「本小程序不收款、不收取任何费用」本意是撇清，
   但每个字都在往界面里塞风险词，而**关键词筛查不认否定**。
   正确做法是**根本不提这件事**，留下「只登记名额」这类正面陈述就够了。
4. 入口只对 `deputy` 及以上可见（和服务端的 `canManage` 一致）。

> **代码注释和文档里仍然叫「义卖」** —— 那是本仓库的内部叫法（repo 名就是 imnu-bazaar），
> 不影响审核。测试只查**用户看得见的文本**：WXML 的文本与属性值、JS 的字符串字面量、
> JSON 的显示字段（`app.json` 的 `description` / `note_*` 除外）。

管理端只是角色和权限，**不改变小程序的主体性质** —— 有管理端不等于"组织运营"。

`tests/miniprogram.test.mjs` 里对这两类词都有拦截，带自测（证明抓得住改错、也放得过注释）。
